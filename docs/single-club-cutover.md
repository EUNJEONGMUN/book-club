# 부글부글 운영 전환·복구 절차

현재는 로컬 검증용 계획이다. 운영에 적용하거나 배포한 상태가 아니다.

2026-11-08 사전 조회·복사 결과와 전체 DB 백업 입력 절차는 `docs/production-preflight.md`에 기록했다. 사전 레코드/파일 복사만으로 최종 백업 조건이 충족되지는 않는다.

## 진행 조건

- 2026-11-08 환경 점검 결과 Preview에 운영 Supabase 주소·키가 공유되고 자동 배포가 켜져 있다. `docs/deployment-readiness-audit.md`에 따라 분리 전에는 새 코드를 push하지 않는다. main의 운영 도메인 자동 연결도 켜져 있으므로 일반 merge를 후보 배포 준비 수단으로 사용하지 않는다.

- 보존 대상은 운영 부글부글 UUID `7504fd29-94ee-4134-b4f6-d7adb25fb2ac`다. 이름으로 대상을 선택하지 않는다. 로컬 시드 UUID와 구분한다.
- 원래 앱·환경 설정·DB·Storage 백업과 복원 검증 결과를 확보한다. `legacy_multiclub`는 원본 계정과 독립된 읽기 전용 보관본이며 외부 백업을 대체하지 않는다.
- 기존 데이터의 계정/프로필 ID, 역할·가입 시각, 일정 ID·발제자·일시·파일 URL/파일명, 질문 순서·본문, 참석, 공개/비공개/익명 평, 초대코드·만료/취소 시각을 비교할 기준을 준비한다.
- Supabase Auth·REST/RPC·Storage에 대한 외부 쓰기를 차단하고 확인할 수 있어야 한다. 앱 점검 화면만 켜는 것으로는 충분하지 않다. 이 외부 차단은 아직 운영에 설정하지 않았으며, 구성·검증 전에는 전환하지 않는다.
- 외부 관리 도구·자동 작업·service-role 쓰기도 중지한다. 진행 담당자와 중단/복구 담당자를 정한다.

## 순서

1. **구 앱에서 점검 모드 준비**
   - 현재 운영 중인 구 스키마 호환 버전에 `scripts/maintenance-bridge.patch`의 점검 응답만 적용한 브리지 배포를 준비한다. 전체 새 앱을 먼저 배포하지 않는다.
   - 환경변수 변경이 기존 배포에 자동 반영된다고 가정하지 않는다. 점검 모드는 DB 클라이언트 생성 전에 응답하므로 구/신 스키마 모두에 동작한다. `MAINTENANCE_MODE=0`이 평상시 값이다.
   - 사전 안내 후 `MAINTENANCE_MODE=1`이 반영된 호환 브리지를 재배포하여 GET 안내·Server Action/API POST 모두 503인지 확인한다. 응답은 no-store, Retry-After 60이다.
2. **모든 외부 쓰기 차단·진행 중 요청 종료 확인**
   - 앱 외에도 Auth의 가입/로그인/토큰 갱신, REST의 INSERT/UPDATE/DELETE 및 RPC, Storage 업로드/교체/삭제를 게이트웨이에서 차단한다. 기존 탭의 직접 SDK 요청도 차단되어야 한다.
   - 기존 유효한 관리자 토큰의 읽기 요청과 파일 다운로드만 검증 경로에서 허용한다. 토큰·키를 로그나 문서에 저장하지 않는다.
   - 게이트웨이 정책·접근 로그에서 실제 차단을 확인하고, 진행 중인 쓰기가 종료되었는지 확인한다. 차단 검증에 실패하면 여기서 중단한다.
3. **최종 백업 및 기준 확정**
   - 쓰기가 중단된 상태에서 전체 DB(인증/보관 스키마 포함)와 Storage 바이트·메타데이터를 백업하고 SHA-256과 시점을 기록한다.
   - 별도 DB에 실제 복원해 읽을 수 있는지 확인한다. 보존 기준을 동일한 스냅샷/중단 구간에서 수집한다.
4. **DB 전환**
   - 적용 예정 마이그레이션 목록을 사전에 확인한다. 새 대상 UUID 검사와 다른 그룹의 일정·관리자 존재 검사를 통과해야 한다.
   - 조회된 미적용 목록인 02 삭제 차단 → 03 단일 모임 전환 → 04 과거 기록/보관본 보호 순서로 적용한다. 각 SQL은 실패 시 자기 트랜잭션을 롤백한다. 전체 절차가 성공했다고 가정하지 않고 실제 적용 버전을 확인한다.
   - 테이블/함수 교체 중에는 구 앱 트래픽을 재개하지 않는다. 단계 사이에도 외부 쓰기 차단을 유지한다.
5. **새 앱의 보호된 후보 배포 확인**
   - 보호된 후보 주소에서 기존 관리자 세션으로 홈·멤버·프로필·과거/미래 일정·자료 다운로드를 조회한다. 운영 도메인은 점검 응답을 유지한다.
   - 전후 기준을 비교한다. 첨부 파일은 URL·파일명뿐 아니라 다운로드 바이트 해시도 확인한다. 익명 표시는 앱에서 작성자 정보가 마스킹되는지 확인한다.
   - 쓰기·탈퇴·관리자 이양 등 변경 시험은 별도의 복원 검증 DB에서만 한다. 운영의 실제 회원·일정으로 시험하지 않는다.
6. **트래픽 전환 및 점검 종료**
   - 데이터 비교·파일 해시·권한·오류 로그가 모두 정상이고 복구 판단이 끝난 뒤에만 재개한다.
   - 게이트웨이의 차단 해제와 새 앱 트래픽 전환을 조정한다. 구 앱으로 쓰기가 재개되는 틈이 없어야 한다.
   - 새 앱의 `MAINTENANCE_MODE=0`을 확인하고 기존 회원의 정상 진입·과거 기록 조회를 확인한다. 이후 오류를 관찰한다.

## 실패 시 복구

- 쓰기를 재개하기 전: 점검/게이트웨이 차단 유지 → 현재 실패 상태도 진단용으로 백업 → 최종 중단 시점 DB·Storage를 함께 복원 → 구 스키마 호환 앱/환경 복원 → 계정·파일·기록 비교 → 확인 후 재개한다. DB만 또는 앱만 되돌리지 않는다.
- 일부 마이그레이션만 성공한 경우도 동일하다. 보관 테이블이 있다고 해서 전체 이전 상태가 자동 복구된 것으로 판단하지 않는다.
- **쓰기를 재개한 뒤: 이전 백업을 즉시 덮어쓰지 않는다.** 다시 쓰기를 차단하고 현재 DB/Storage를 별도 보존한다. 재개 이후 새 가입·수정·파일을 추출해 병합/복구 계획을 검증하기 전까지 복원을 실행하지 않는다.
- 보관 스키마·기존 백업은 안정화가 끝나도 자동 삭제하지 않는다. 별도의 보존 정책과 검증을 거쳐 결정한다.

## 로컬 재현

```bash
node scripts/check-local-records.mjs snapshot .local-backups/검증-전.json
pnpm test
pnpm test:integration
node scripts/rehearse-single-club.mjs .local-backups/기존-다중모임-백업/database.dump
pnpm test:e2e
node scripts/check-local-records.mjs compare .local-backups/검증-전.json
```

리허설은 고정 로컬 Docker 컨테이너에 새 임시 DB를 만들어 복원하며, 원래 로컬 DB를 초기화하지 않는다. 파일 시험은 생성한 랜덤 경로의 PDF 하나만 추가/다운로드/정리한다. 기존 파일·계정·기록은 수정하지 않는다. 운영 URL 입력은 거절한다.

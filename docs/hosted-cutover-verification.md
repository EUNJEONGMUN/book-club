## 시험 대상을 나눈 이유

- 기존 관리형 Preview DB `postgres`: 실제 Auth·REST·Storage의 차단·읽기·백업·해제를 확인했다. 모든 쓰기 요청은 새 임시 계정과 `cutover-test-<실행ID>/` 아래 새 파일만 대상으로 했다. 기존 사용자·일정·파일을 수정 시험에 사용하지 않았다.
- 같은 **테스트 프로젝트에 새로 만든 별도 DB**: 다중 모임의 구 구조에서 02→03→04 적용과 실패/복구를 시험했다. 검증된 백업에서 **스키마 정의만** 추출하고 계정·일정·평·초대 등은 모두 합성 값으로 채웠다. 운영 회원 데이터·비밀번호 해시·파일 바이트를 테스트 클라우드에 업로드하지 않았다.
- 외부 네트워크·공개 포트가 없는 새 로컬 컨테이너 두 개: 합성 DB와 실제 Preview의 차단 중 전체 백업을 각각 복원하고 모든 비교 대상 행을 대조했다. 시험 후 해당 컨테이너는 정리했다. 기존 로컬 DB는 복원 대상이 아니다.

새 DB의 Auth/Storage 테이블은 스키마 정의를 새 소유자로 설치했으므로 실제 관리형 서비스와 소유권이 다르다. 따라서 실제 API·관리형 권한의 차단 검증은 기존 Preview에서 별도로 수행했다. 합성 DB에 HTTP 서비스를 연결해 로그인까지 했다고 주장하지 않는다.

## 발견·보완한 점

1. 관리형 백업의 스키마 필터 추출에는 Auth/Storage 스키마 생성문이 빠질 수 있었다. 합성 DB를 초기화할 때는 빈 스키마를 먼저 준비하고, 전체 복원에서는 아카이브에 이미 포함된 스키마를 다시 만들지 않도록 구분했다.
2. 교체 직후 같은 URL로 읽으면 캐시된 이전 응답이 반환될 수 있었다. 검증 도구에서 파일 GET마다 `cacheNonce`와 `no-cache`를 적용한 뒤 실제 바이트를 대조해 통과했다. 앱 URL·파일·캐시 설정을 변경한 것은 아니다. **당일 최종 파일 백업 도구에도 캐시 우회와 메타데이터/버전 전후 비교가 필요하다.** 기존 온라인 복사 도구를 그대로 최종 백업 도구로 사용하지 않는다. [Supabase 캐시 우회 설명](https://supabase.com/docs/guides/storage/cdn/smart-cdn#bypassing-cache).
3. 세션 풀러가 임시 DB의 유휴 연결을 보관하므로 일반 DB 삭제가 실패할 수 있었다. 이를 위해 기존 서비스 연결을 일괄 종료하거나 FORCE 삭제하지 않았다. 현재 도구는 합성 DB를 자동 삭제하지 않고 최종 백업과 실행 식별자를 보관한다.
4. 도중 실패한 시험의 새 계정/보이는 파일은 정확한 실행 표시·ID·경로를 확인해 정리했다. 첫 실패에서 완료되지 않은 TUS의 비공개 임시 리소스는 관리형 만료까지 남을 수 있다. 완료된 원래 파일이나 원래 DB 행이 아니며 기존 데이터를 수정하지 않았다. 마지막 성공 시험의 TUS는 재개·완료·바이트 확인 후 보이는 파일을 정리했다.

## 남아 있는 경계

- 이번 관리형 시험은 비밀번호 Auth, REST, 표준/서명/TUS 파일 경로다. S3 단일/분할·SECURITY DEFINER RPC의 차단/해제는 앞선 같은 서비스 버전의 로컬 40개 흐름에서 확인했다. **관리형 S3와 실제 Google 로그인 차단/재개는 이번에 다시 시험하지 않았다.**
- 차단 COMMIT 시점에 이미 HTTP 본문을 보내는 요청을 강제로 끊은 실험은 아니다. 실제 점검 시에는 진행 중 업로드 종료, 다른 직접 postgres 관리 작업 중단을 별도로 확인해야 한다.
- 여기서 검증한 실행 도구는 **테스트 전용**이다. 운영 접속 경로는 허용하지 않았다. 운영에 사용할 때는 실제 대상·당일 적용 이력·동일 차단 구간의 최종 백업/복원 증거와 배포 절차를 연결한 실행 계획을 별도로 검토해야 한다. 테스트 결과로 운영 실행 승인이 생기지 않는다.
- 운영 점검 시간·담당자·배포 후보/복구 앱·별도 승인·당일 최종 백업과 보존 비교는 남아 있다. `production_ready=false`를 유지한다.

## 임시 합성 DB 정리 상태

중간 실패 5개와 마지막 성공 1개, 총 **6개의 새 합성 DB**를 전체 백업하고 실행 ID·합성 계정만 존재함을 읽기 전용으로 확인했다. 자동 승인 검토가 원격 DB 일괄 삭제를 거절했으므로 삭제하지 않았다. 사용자에게 정확한 6개 목록으로 정리 승인을 요청했으며 답변 전에는 보관한다. 기존 테스트 DB `postgres`와 운영 DB는 이 목록에서 제외된다. 목록/백업 해시는 같은 증거 폴더의 `cleanup-inventory.json`이다. 삭제는 검증 통과의 조건이 아니며 백업을 포함한 시험 증거는 삭제 대상이 아니다.

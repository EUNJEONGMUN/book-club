# 운영 실행·최종 백업·복원 검증 연결 — 2026-11-10

**후속 사용자 결정:** 로그아웃을 허용하고 운영 전환·배포를 승인받은 뒤 소유자 수동 실행으로 전환했다. 현재는 [수동 운영 전환](manual-production-cutover.md)의 단계와 검증 결과를 우선한다. 아래 무조건 보류 설명은 로그인 유지 요구가 있던 당시의 기록이며 SDK 동작이 해결됐다는 뜻은 아니다.

**연결 코드와 격리 검증을 준비했지만 실제 운영 실행은 차단해 두었다.** 전체 Auth 쓰기 차단 때 발생하는 HTTP 500이 현재 SDK의 브라우저 로그인 정보를 지울 수 있음을 재현했기 때문이다. 운영 DB·배포에는 적용하지 않았다. 이 문제를 해결하기 전에는 점검/쓰기 차단·실제 전환을 시작하지 않는다.

## 연결한 도구

| 도구 | 역할 |
|---|---|
| `production-cutover.py` | 기본 실행/실행 계획 생성은 오프라인. 고정 운영 대상·릴리스·실행 ID를 묶고 단계별 명령만 제공. 배포 명령·임의 SQL·계정/DB 삭제 기능 없음 |
| `cutover-io.py` | 기존 DB 비밀번호를 인자/파일에 저장하지 않는 별도 운영 전송 계층. 고정 프로젝트·세션 풀러·DB/역할·TLS 검증. 파일 GET마다 캐시 우회. 원래 키를 읽기만 하며 발급/재설정하지 않음 |
| `cutover-engine.py` | 서버에 단계·실행 ID·릴리스/백업/복원 해시를 기록. 차단→백업/실제 복원→02/03/04→보존 비교→복구/재개를 연결 |
| `verify-cutover-backup.py` | 완료된 최종 백업 묶음을 새 네트워크 없는 로컬 컨테이너에 실제 복원. 전체/복구용 public 아카이브·모든 행/시퀀스·파일을 검증 |
| `rehearse-operational-cutover.py` | 운영과 같은 DB명/클럽 UUID의 별도 로컬 복원본에서 위 엔진을 그대로 시험. 실제 운영/클라우드 연결 없음 |
| `check-cutover-session-risk.mjs` | 설치된 SDK의 HTTP 500/503 세션 동작을 실제 네트워크 없는 합성 응답으로 확인 |

기존 로컬/관리형 시험 도구의 운영 대상 거절 제한은 풀지 않았다. 앱·DB 마이그레이션·환경·의존성도 변경하지 않았다.

## 백업이 전환을 허용하는 조건

1. 기존 부글부글 UUID, DB `postgres`, 비슈퍼유저 `postgres`, PostgreSQL17, 적용 이력이 기준과 같아야 한다. 다른 실행/남은 보관 상태/예상 밖 관리형 의존성은 중단한다.
2. 서버에 저장한 실행 ID·릴리스 해시와 단계가 맞아야 한다. 실제 차단 함수 본문·소유자·보안 설정·API 권한, 트리거 종류/활성 상태·모든 보호 대상, 진행 중 S3·벡터 기능을 검사한다.
3. 같은 차단 구간에서 전체 DB와 public 복구용 dump, 비교 대상 행·권한/정책/기본 권한/Realtime 기준, Storage 메타데이터·원본 파일을 수집한다. 캐시를 우회해 파일을 두 번 읽고 해시를 대조한다. 모든 사본이 성공하고 전후 차단/행/정책이 같을 때만 완료 manifest를 쓴다.
4. **복원 보고서가 있다는 이유만으로 진행하지 않는다.** 승인 단계가 복원 검증기를 직접 실행한다. 새 로컬 컨테이너에서 전체 아카이브의 모든 COPY 블록·시퀀스를 비교하고, 별도 public 복구용 아카이브도 새 DB에 실제 복원한다. RLS 정의와 파일 바이트도 대조한다.
5. 전체 아카이브 안에 해당 실행 ID/릴리스/차단 시각의 제어 행이 실제로 들어 있어야 한다. 옛 온라인 dump에 외부 JSON만 붙인 사본은 이 검사를 통과하지 못한다. 로컬 증거는 운영 연결의 증거로 사용할 수 없다.
6. 복원 후에도 현재 행·정책·파일·차단을 다시 비교한다. 서버의 `backup_verified` 단계에 **그 manifest와 실제 복원 결과의 해시**가 기록된 뒤에만 SQL을 허용한다. 이후 비교·복구·재개도 같은 서버 승인 백업에 묶인다.

02→03→04의 원래 SQL 이름/해시를 고정한다. 각 트랜잭션의 COMMIT 전에 새 테이블 보호·적용 이력·다음 단계를 기록한다. 오류 시 데이터·정책·이력·단계가 함께 롤백되고 자동 재시도하지 않는다.

기존 온라인 운영 백업은 그대로 유지했다. 현재 생성한 새 백업은 **로컬 복원본의 시험 백업**이고 운영의 당일 최종 백업이 아니다. 최종 manifest나 로컬 계획은 사용자 승인 문서/전자서명이 아니다.

## 중단·복구·재개

- **전환 전 취소:** 아직 02도 적용하지 않았을 때만 원래 DB 구조/이력을 확인하고, 현재 데이터를 복원하거나 덮어쓰지 않고 임시 차단을 해제할 수 있다. 원래 앱/도메인 확인이 선행돼야 한다.
- **부분/전체 전환 후 복구:** 쓰기 차단을 유지하고 실패 당시 전체 DB/행도 보존한다. 전환된 앱 객체·적용 이력을 비공개로 격리한 뒤 최종 public 사본으로 원래 구조·업무 기록·정책·권한/이력을 복구한다. public 스키마 OID/기본 권한·Auth·Storage 데이터와 파일은 유지한다.
- **실패 보관본 추가 보호:** 격리/보관 테이블의 외부 FK를 분리하고 영구 쓰기 거절 트리거를 둔다. 임시 차단을 해제한 뒤 실제 회원 계정 삭제에 따라 실패 보관본도 같이 지워지는 경로를 막는다. 새 합성 계정의 삭제를 롤백하는 시험으로 확인했다.
- **복구 후 확인 실패:** DB 단계는 `recovering`에 남고 재개할 수 없다. 검증을 모두 통과한 `recovered_verified`와 구 앱/도메인 확인이 있어야 차단을 푼다. 일부만 성공한 복구를 완료로 처리하지 않는다.
- **쓰기 재개 후:** 이전 백업 복구를 거절한다. 다시 차단하고 현재 기록/파일 보존·병합 계획부터 검토해야 한다.

도구는 임의의 DB 전체 덮어쓰기, Auth/Storage 데이터 초기화, 회원/파일 삭제, 키/비밀번호 교체, Vercel 승격을 수행하지 않는다. 잘못된 단계나 오류가 나면 비정상 종료하고 현재 차단/상태를 남긴다.

## 새로 확인한 운영 차단 사유

관리형 시험에서 Auth 갱신 요청은 차단 중 HTTP **500**을 반환했다. 설치된 `@supabase/auth-js 2.106.2`로 합성 응답을 주어 확인한 결과:

| 응답 | SDK의 동작 |
|---|---|
| 갱신 HTTP 500 | 저장한 세션 제거, `SIGNED_OUT` 발생 |
| 갱신 HTTP 503 후 정상 응답 | 재시도 후 세션 유지, 강제 로그아웃 없음 |

검사 보고서는 `.local-backups/session-risk-20261109T153026788Z/verification-report.json`이다. 실제 서버/토큰/사용자 계정은 쓰지 않았다. 이는 **백엔드 계정·기록이 보존되는 것과 브라우저의 로그인 상태가 유지되는 것이 다르다**는 확인이다. 이전 40/337개 서버 요청 검사는 브라우저 SDK의 이 동작까지 검증한 결과가 아니었다.

기존 사용자에게 불편을 주지 않는다는 요구에 따라 `production-cutover.py`의 실제 운영 세션은 **명시적 실행 플래그가 있어도 자격증명을 읽기 전에 거절**한다. `PRODUCTION_EXECUTION_ENABLED=False`이며 준비/격리 시험만 가능하다. 플래그나 문서의 확인 값을 바꾸는 것으로 해결된 것으로 취급하지 않는다.

다음 보완은 **인증 갱신을 유지하면서 업무·파일 쓰기와 계정 삭제/식별자 변경을 보호하는 차단 설계**를 검토하고, 실제 Auth 서비스/SDK와 동시 갱신 중 백업 정합성을 검증하는 것이다. 이미 열린 구 버전 탭도 고려해야 하므로 새 앱의 응답 처리만 바꾸고 끝났다고 판단하지 않는다. 운영의 Auth 설정·키·사용자 계정을 바꾸는 조치는 하지 않았다.

## 사용 범위

현재 허용하는 실행은 준비·로컬 검증뿐이다:

```bash
python3 -B scripts/production-cutover.py --prepare-run
python3 -B -m unittest discover -s tests/scripts -p 'test_*.py'
python3 -B scripts/rehearse-operational-cutover.py
/opt/homebrew/opt/node@24/bin/node scripts/check-cutover-session-risk.mjs
```

운영 연결 코드는 별도로 마련했지만 이번에는 실행하지 않았다. 기본 읽기 전용과 소유자 터미널의 숨김 입력, 고정 프로젝트/DB/TLS, 실행 단계/증거 확인이 필요하다. HTTP 전송 중 작업 종료·다른 운영자 작업 중지·실제 관리자 세션 확인은 외부 운영자의 실제 점검이 필요하며 JSON의 `true`만으로 자동 입증되지 않는다. 배포 후보 생성·점검 일정·별도 운영 승인도 여전히 남아 있다. **현재는 운영 실행 승인을 요청하는 단계가 아니다.**

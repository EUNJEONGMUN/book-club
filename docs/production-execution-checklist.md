## 실행 전 남은 준비

1. **관리형 테스트 환경의 실행 경로 검증:** 현재 SQL 생성기는 고정된 로컬 DB 두 개만 허용하며 운영 DB명 `postgres`를 거절한다. 이 제한을 풀어 운영에 바로 쓰지 않는다. 프로젝트/DB/클럽/서비스 역할·테이블·적용 이력과 단계별 성공 증거를 검사하는 운영용 실행 경로를 별도로 준비하고, 관리형 Preview에서 설치·차단·백업·해제 및 실패 복구를 시험한다. 테스트 회원·파일도 전후 대조하며 원래 상태로 돌린다. 현재 이 관리형 시험이나 운영 실행기 준비가 끝났다고 주장하지 않는다.
2. **배포 후보·복구 앱 준비:** 구 앱+점검 패치와 새 앱의 보호된 후보, 각 환경 적용 범위와 복구 대상을 검토한다. main 자동 운영 배포가 켜져 있으므로 준비를 위해 main에 병합하지 않는다. 새 앱을 구 운영 DB에 미리 연결해 공개하지 않는다. 실제 배포 생성·운영 연결 변경은 별도 승인 후다.
3. **점검 시간·담당자·승인 확정:** 사용자 안내 시간, 진행 담당자, 복구 판단 담당자를 정하고 예상 중단과 복구 방식을 설명한 뒤 운영 실행을 승인받는다. 비밀번호·키를 재발급하는 절차가 아니다.

## 중단과 복구의 경계

- **DB 전환 전 중단:** 점검/차단을 유지하며 실패 원인을 확인한다. DB가 원래 구조·원본 그대로인지 확인한 뒤 구 앱을 유지하고 차단을 해제할 수 있다. 실패한 차단 설치 트랜잭션은 전체 롤백 여부부터 확인한다.
- **전환 후, 쓰기 재개 전 실패:** 현재 실패 상태도 별도 백업하고 보존한다. 시험한 방식대로 전환 앱 객체·새 이력을 비공개로 옮기고, **당일 최종 public 백업**으로 구 앱 구조·업무 데이터·RLS/Storage 정책·원래 적용 이력을 복구한다. public 스키마 OID·관리형 기본 권한과 Auth/Storage 레코드·파일은 유지한다. 구 앱 호환성과 모든 원본을 다시 대조하기 전 차단을 풀지 않는다. 일부 SQL만 적용된 경우도 실제 이력에 맞춰 판단하며 파일 이름만 보고 성공으로 처리하지 않는다.
- **쓰기 재개 후 실패:** 다시 차단하고 현재 DB/파일부터 새로 보존한다. 재개 이후 가입·수정·업로드를 대조·병합하는 계획을 검증한다. 예전 사본으로 즉시 덮어쓰지 않는다.
- **예상 밖 Auth/Storage 자체 손상:** public 복구만으로 해결됐다고 판단하지 않는다. 전체 백업·파일을 함께 보존하고 별도의 복구 범위를 먼저 검증한다. 관리형 스키마 전체 교체를 즉흥적으로 시도하지 않는다.

공통 중단 기준은 대상 불일치, 승인 없는 변경, 백업/복원/파일 대조 실패, 진행 중 쓰기 미확인, 보호 누락, 새 기록 손실 가능성이다. 중단은 삭제·초기화·비밀번호 재설정·이전 백업 덮어쓰기를 의미하지 않는다. 기존 보관본·실패 사본·백업은 자동 삭제하지 않는다.

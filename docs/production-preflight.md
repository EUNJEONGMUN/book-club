`manifest.json`에 기록된 19개 파일의 크기와 SHA-256을 다시 검증했고, 저장소 메타데이터가 다운로드 전후 동일한 것을 확인했다. 저장소 파일은 실제 바이트와 메타데이터 크기도 대조했다.

**이것은 운영 사용 중의 사전 복사본이다. 전체 DB 구조·역할을 복원하는 백업이나 최종 전환 기준점이 아니다.** 계정 로그인 등 운영 쓰기를 중단하지 않았으므로 서로 다른 요청 시점의 정보가 포함된다. DB 아카이브 확보와 실제 복원 검증을 완료하기 전에는 운영 전환하지 않는다.

## 전체 DB 아카이브 확보 — 완료

사용자가 터미널에서 백업 도구를 실행해 `.local-backups/production-dump-20261108T052113760121Z/database.dump`를 생성했다. 크기 511,582바이트와 SHA-256을 확인했다. 이후 외부 네트워크가 없는 별도 로컬 컨테이너에 전체 복원했고, 아카이브의 모든 테이블 데이터 블록 49개·시퀀스 위치 2개·정책·파일 14개를 대조했다. 복원본의 단일 모임 전환까지 포함한 226개 검사를 통과했다. 원래 dump와 manifest는 유지하고 옆에 `restore-verification.json` 확인서를 추가했다.

아래는 백업 도구 사용법과 당시 연결 문제의 수정 기록이다.

사용자가 기존 운영 DB 비밀번호를 보관하고 있음을 확인했다. 비밀번호 재설정은 하지 않는다. 본인 터미널의 프로젝트 폴더에서 실행한다.

```bash
python3 scripts/production-db-dump.py
```

도구는 기존 비밀번호를 숨김 입력받는다. 고정된 운영 프로젝트의 세션 풀러에 인증서·호스트 검증을 하는 연결을 열고, 읽기 전용 설정을 확인한 후 로컬 Docker의 PostgreSQL 도구로 `pg_dump` 아카이브를 만든다. 비밀번호는 메모리와 로컬 프로세스 입력에서만 전달하며 인자·파일·로그에는 남기지 않는다. DB 역할 생성·비밀번호 재설정·마이그레이션은 실행하지 않는다.

2026-11-08 실행 중 발견된 인증서 오류를 수정했다. 시스템 CA만 사용하던 연결에 공식 Supabase Root 2021 CA를 추가했으며, 인증서·호스트 검증을 유지한다. `python3 scripts/production-db-dump.py --diagnose`로 비밀번호 없이 실제 운영 접속 경로의 TLS 검증을 통과했다. 이 진단은 비밀번호 인증 성공이나 덤프 완료를 뜻하지 않는다. 공개 인증서 원본·해시는 `scripts/certificates/README.md`에 기록했다. 오류는 인증서/비밀번호/DNS/네트워크/Docker 등으로 구분하며 원시 오류나 비밀값을 출력하지 않는다.

이후 사용자의 연결은 성공했지만 기존 도구의 읽기 전용 확인 조건에서 중단됐다. 접속 시작 옵션(`PGOPTIONS`)의 전달 여부를 가정하지 않도록 바꿨다. 이제 `BEGIN READ ONLY` 안에서 읽기 전용 상태·DB 이름·보존 대상 부글부글 ID를 JSON으로 확인하고 `ROLLBACK`한다. DB나 역할의 기본 설정은 바꾸지 않는다. 실제 덤프는 PostgreSQL `pg_dump` 자체의 `REPEATABLE READ, READ ONLY` 트랜잭션을 사용하며, 잠금 대기 제한도 도구의 `--lock-wait-timeout=5s` 옵션으로 적용한다. [PostgreSQL 17 구현 근거](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/bin/pg_dump/pg_dump.c).

로컬의 새 임시 DB에서 기본 읽기 전용 설정이 `off`인 상태로 시작해 명시적 트랜잭션의 `on` 응답, 쓰기 차단, 아카이브 생성·목록 확인·다른 임시 DB에 복원, 원본/복원 기록 일치를 검증했다. 시험 후 원래 기본 설정은 `off`였고 생성한 시험 DB만 정리했다. 관련 안전 가드 단위 테스트 9개도 통과했다. 이후 사용자 터미널에서의 실제 운영 덤프도 성공했다.

성공하면 새 `.local-backups/production-dump-…/` 아래에 `database.dump`, `database.contents.txt`, SHA-256이 담긴 `manifest.json`이 생긴다. 실패 시 완료 manifest가 생성되지 않으며 부분 파일을 복구본으로 사용하지 않는다.

이 아카이브에는 Storage 실제 바이트와 클러스터 역할이 포함되지 않는다. 앞서 내려받은 파일 사본을 함께 보존하고, 역할·소유권·권한 호환성을 검토해야 한다. 실제 복원 검증까지 완료되어야 복구 가능하다고 판단한다.

운영 역할·Vercel 환경 읽기 전용 점검도 완료했다. 비슈퍼유저 `postgres`로 별도 운영 복원본에 전환을 실행해 228개 보존 검사를 통과했다. 당시 Vercel은 Supabase 세 변수를 Production/Preview 공용으로 설정 중이었고 이후 위와 같이 분리했다. Preview 자동 배포와 main 운영 도메인 자동 연결은 계속 켜져 있다. 당시 점검 기록은 `docs/deployment-readiness-audit.md`를 따른다.

1. **완료:** 생성한 운영 DB 아카이브와 파일을 격리된 로컬 DB·저장 경로에 복원했다. 원래 로컬 DB는 초기화하지 않았다.
2. **완료:** 원본 백업의 전체 레코드·권한·계정·파일 바이트와 02→03→04 적용 후 데이터 보존을 대조했다. 이후 별도 로컬 Auth/REST/Storage와 임시 계정으로 이메일 로그인·세션 갱신·파일 HTTP·브라우저 다운로드도 검증했다(18개 흐름, 92개 보존 검사). 결과는 `docs/local-service-flow-verification.md`. 실제 Google 인증과 앱의 인증된 이름 등록 화면까지도 확인했다. 운영 역할 카탈로그 조회와 해당 권한의 로컬 리허설도 완료했다. 새 로컬 프로필 등록/승인은 제출하지 않았다.
3. **신규 Preview 연결 분리 및 실제 핵심 앱·Google 인증 검증 완료.** 운영 전환 중 외부 Auth/REST/RPC/Storage 쓰기 차단 수단 확정·시험은 남아 있다. 현재 외부 쓰기 차단은 미구성 상태이며 읽기 전용 기본값·DB IP 제한으로 대체할 수 없다.
4. 별도 운영 반영 승인 후에만 점검·쓰기 중단, 최종 DB/파일 백업, 재검증, DB 전환, 새 앱 배포, 비교, 서비스 재개를 진행한다. 구체적인 순서와 복구 기준은 `docs/single-club-cutover.md`를 따른다.

Google 로그인 후속: 로컬 설정과 실패/취소 안내·목적지 보존·위험한 이동 주소 차단을 검증했다. 전체 단위 66개·타입 검사·분리 빌드 통과. 이후 사용자가 실제 Google 인증을 완료해 인증된 이름 입력 화면(`/signup`)에 도착했다. 새 로컬 계정/Google identity 각 1개만 생성됐고 원래 기록·인증 정보·운영 백업은 보존됐다. 같은 Google 제공자 식별자의 운영 프로필/관리자 멤버십도 백업에서 확인했다. 새 로컬 이름 등록·모임 가입 승인은 제출하지 않았다. 상세 `docs/google-oauth-check.md`.
